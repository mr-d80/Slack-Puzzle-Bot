# Development Notes

## 2026-04-08

- Preserve the AI rewrite for daily recaps, but make required facts explicit in the prompt and allow one AI revision pass if a mandatory callout is missing.
- Slack NL queries are now opt-in through the `bot:` prefix only. Broad `?` and keyword heuristics were too noisy in a score-reporting channel.

## 2026-05-07

- NL-query trigger broadened from `bot:` only to also accept `bot,` and a leading `?` (with or without trailing space). Users repeatedly tried `?` and were getting silent drops; the rule "no broad heuristics" still holds — bare text without one of those explicit prefixes is still ignored.
- Rule-based translator now extracts relative windows (`last N days/weeks/months`, number-words like `last two weeks`, `over the last 14 days`) and explicit ISO ranges (`range/between/from … to/and/through …`) into `date_range.start`/`end` at translate time. Previously only the literal strings `last 7 days` and `last 30 days` were recognized; everything else fell through to `all_time`.
- Rule-based translator now honors `<@U…>` mentions as the target user across all user-centric intents, and recognizes natural phrasings (`how'd I do`, `how did <@user> do`, `what are my/<@user>'s results`, `my/<@user>'s performance`, `win frequency`) that previously fell to the LLM and frequently came back as `unsupported`.
- New `NLQueries` worksheet: every NL query is appended with the parsed intent, target user, resolved date window, and response prefix. Lets us debug "wrong answer" complaints from the spreadsheet alone instead of correlating Slack timestamps with file logs.

## 2026-07-29

- Monthly summaries are event-driven, not scheduled. The bot has no scheduler — nothing runs unless a Slack message arrives — so the month rollover hangs off `finalize_due_days`: after a day is actually finalized, we check for finished months with no `MonthlyResults` row.
- "Finished" is deliberately not "the clock says the month ended" (`month_is_final`). A month is finished the moment its **last day is finalized**, because a posted day never re-finalizes, so nothing further can land in that month. `finalize_day` posts a day as soon as every expected player completes, so on a normal 30th the June wrap goes out that evening rather than waiting for someone to play on July 1. The wall-clock check remains as the backstop for a final day nobody played (it never finalizes, so the fast path can't fire) or a restart that missed it.
- What that does **not** fix: if the last day of the month is only partly played, it stays `not_ready` until the day closes at midnight, and nothing notices midnight until the next message arrives — which is a message in the new month. Nothing runs without inbound Slack traffic, so that residual gap can only be closed by a scheduler, which would mean a second always-on process.
- The rollover check is gated on a day having been finalized, not on every message. Ungated it would cost two sheet reads per score post, which is the pattern that produced the 429 storms we spent v4.6.2 fixing.
- The `MONTHLY_SUMMARY_MAX_AGE_DAYS` limit (default 14) exists purely because `MonthlyResults` starts empty. "Unposted" and "should be posted" are the same predicate to `due_months`, so on the first rollover after deploying, every month in the existing `DailyResults` ledger qualifies and the bot would post the entire back catalogue in one burst. The limit is measured from the month's last day, so deploying mid-July stays quiet (June is 29 days stale) and then wraps July normally on the 31st. Skipped months are logged and left unclaimed rather than silently marked posted, so they remain available to `--month`. The tradeoff: an outage spanning a month boundary by more than 14 days means that month needs posting by hand.
- `MonthlyResults` is claimed before posting, not after. Posting first and recording second means a Slack failure halfway through the thread reposts the whole month on the next score. Claiming first means the worst case is a partially-threaded month, which is recoverable with `python monthly_summary.py --month YYYY-MM --post --force`.
- Pinpoint is excluded from the skunk metric for a units reason, not a magnitude one. The skunk is the largest last-place margin across games; Pinpoint's margin is guesses plus a +100 DNF penalty, everyone else's is seconds. Audited over June–July 2026, Pinpoint won only 1 of 40 skunks — so it was not swamping the metric, it was just being ranked against an incomparable quantity. Filtering happens both at detection and in `monthly_summary._accumulate`, because days finalized before the change keep their original skunk on the sheet. An excluded day contributes nothing rather than falling back to the day's runner-up skunk: only the top one is stored in `recap_facts`, so the runner-up isn't recoverable.
- That audit is also the answer to "why is the champion also the skunk king?" — it's real. Over June–July the June winner was skunked in Queens ×7, Crossclimb ×6, Tango ×4, Zip ×2 while taking Mini Sudoku 19 times in June alone. The league has specialists, and the metric is reporting that correctly rather than misfiring.
- Month records are computed as the minimum daily `best_value` per game. That relies on the league-wide rule that lower is always better (including Pinpoint, where a DNF carries a +100 penalty so it can never win). If a game with higher-is-better scoring is ever registered, `_collect_records` needs a metric-direction check.
- The monthly AI wrap falls back to the deterministic template when a required callout survives neither the rewrite nor the revision pass. This differs from the daily recap, which keeps the AI text in that case. Rationale: a daily recap missing the skunk line is a lesser problem than a month wrap that fails to name the champion.

## 2026-09-30

- Scoring moves from trophy/necktie to a 3/2/1 podium on **2026-10-01**. The cut-over is keyed on the *score day* (`awards.uses_medal_scoring(day)`), never on when finalization runs: a day that closes after midnight, a late reconcile, and a forced re-finalize of an old day all have to score under the rules the day was played under. `compute_daily_winners` takes `day` explicitly from `finalize_day`, `backfill_daily_ledger_from_scores` and `reconcile_day`, falls back to the day on the records, and gives the legacy rules to records that name no single day, so an old caller can't start awarding points by accident.
- `DailyResults` is never rewritten, so two award shapes live in the ledger indefinitely: `{wins, ties}` before the cut-over and `{gold, silver, bronze, points}` after. `awards.AwardTally` reads either (and the bare int in the oldest rows) and adds across them. Its `rank_key` is `(points, gold, silver, bronze, wins, ties)`, which for a legacy-only tally orders by `(wins, ties)` exactly as the standings always did. Five modules each had their own inline copy of the `wins`/`ties` parsing; they all go through it now. `sheet_store.unpack_award_value` was deleted rather than kept: a `(wins, ties)` pair can't represent medals, so a caller left on it would have read every medal day as zeros without an error.
- `awards.py` imports nothing from the project because `insights`, `nl_query`, `weekly_summaries` and `recap_commands` deliberately don't import `config` (which needs `SPREADSHEET_ID` at import). `MEDAL_SCORING_START` is read from the environment on each call, not at import, for the same reason: `config` loads `.env` on import, and a module that never imports it would have captured the default before the override applied.
- Olympic ranking: `scoring.rank_finishers` groups a game's finishers by result, and a group's place is the number of players ahead of it plus one, so two firsts are followed by a third. Points belong to the place, not the player, so a tie never splits the points of the places it covers, and anything past third scores nothing.
- The tiebreak now splits ties at every place. Applying it only to first would have ranked a tied second by arrival order even when tiebreak data existed. The rule that it needs data from *every* tied player is unchanged.
- A Pinpoint DNF (scored as guesses + 100) can't take a medal. "A DNF can never win" only held because the +100 sorts it last; with three medals it would hold only when three or more players solved the puzzle, and a bronze for a concession is the one outcome nobody would defend. A game nobody finished has no result at all. DNF is detected as a *guesses* game at or past the penalty, not as a bare threshold, because a time game legitimately runs past 100 seconds.
- A sole finisher still takes gold. That is what the old code did (a lone player simply won the game).
- Month wrap: the cut-over month drops its month-over-month comparison, because September's trophies and October's points aren't the same quantity; November compares points with points. The AI prompt's photo-finish (<=2) and runaway (>=10) cut-offs were tuned in trophies, so in a points month they scale by what a first place is worth rather than calling every month a runaway. Standings share a place only when level on points *and* on the gold/silver/bronze count-back. The margin is in points, so a champion who won on count-back has a margin of 0 and the wrap says "level on points". A month's scoring is read off the days actually posted (its first day only decides a month with nothing posted), so moving the cut-over mid-month for a test still renders a month of medal days as medals.
- Windows that cross the cut-over (all-time and last-30-days NL queries, a weekly summary that straddles it) show both families of award side by side and never add trophies to points. NL "wins" mean first-place finishes (trophies plus golds), so a strikeout is still "a day with no first place" in both eras, and the single-day record is computed per era. Leaderboards rank two ways because the two questions differ. A *wins* question ("who wins Zip most often?", which defaults to all-time) ranks by first-place finishes and then points, the only ordering that means the same thing on both sides of the cut-over; ranking it by points would bury years of trophies under a few days of medals. A *points* question ranks by points and then the gold/silver/bronze count-back, and defaults to this month.
- The medal emoji are Slack's built-in `:first_place_medal:` and friends, not the GitHub-style `:1st_place_medal:` the change was specified with, which Slack doesn't resolve (it would post as literal text). They are three constants in `awards.py`.
- How it was checked: because the bot posts September's results and wrap from the same code that starts scoring October, the new `scoring.py`, `insights.py`, `monthly_summary.py`, `weekly_summaries.py` and `recap_commands.py` were run against the committed versions on randomised legacy ledgers, and every legacy day, month, AI prompt and weekly message came out identical. The one difference is the order of players with identical running totals: it used to follow set-iteration order, so it varied from run to run, and is now by user id. `nl_query.py` had no comparable baseline (it carries uncommitted work), so its legacy answer formats are pinned by golden tests instead.
- Known limits. `_ensure_cols` now widens a sheet that is narrower than the header it is about to write, because the Sheets API rejects a write past the grid and the new Totals columns are added at startup, where a failure would stop the bot from starting (a default 26-column sheet never needs it). The cut-over is assumed to fall on a month boundary; a mid-month `MEDAL_SCORING_START` logs a warning when a month mixes both scorings. Five older executors in `nl_query.py` (`_wins_leaderboard`, `_best_week`, `_all_games_awards_leaderboard`, `_user_game_awards`, `_all_time_stats`) have no callers and still render trophies; they were left alone. The bot has to be restarted onto this code before the first October day finalizes: a day finalized by the old process is stored with trophy-shaped awards and has to be re-finalized (`/jw-recap 2026-10-01 --force`) to be re-scored.
